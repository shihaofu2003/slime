# OPD 代码与实验检查（2026-09-22）

目的：检查 `tau2-opd-airline-retail-pilot` 的蒸馏目标、异步采样、教师打分和评测结论。
范围：v1 job22764、v2 job22822、当前 v3 代码，以及 SFT4505 / Airline iter29 / Retail iter9 的已有评测。检查期间 v3 job22858 已启动；本文不把其未完成的训练当作评测证据。

## 结论

优先处理两个问题：**v3 的 behavior-logprob 替换并非当前学生 reverse-KL 的无偏修复；异步 producer 的完成队列没有受 pool32/pending64 约束，造成明显陈旧采样。** 前者是 v3 新增问题，不能解释已经完成的 v1/v2 结果；后者在两次已完成试验中均有日志证据。现有材料不能证明 Airline 差距已经触及蒸馏能力上限，也不能证明 v2 的退化仅由 policy lag 导致。

本次补充本报告、[复算脚本](review_20260922.py)、[结果](review_20260922_results.json)和 README 入口，未改训练实现、启动或停止集群任务。复算命令：`python3 output/experiments/tau2-opd-airline-retail-pilot/review_20260922.py`。脚本读取已有训练日志和轨迹，在 CPU 上调用从当前源码提取的实际 loss 函数；不请求模型服务。

## 1. 高优先级：v3 改变了目标，负日志值不等于旧梯度方向错误

代码位置：[loss.py](../../../slime/backends/megatron_utils/loss.py)，`compute_advantages_and_returns` 第765–779行、`vanilla_tis_function` 第837–860行；[默认开关](../../../examples/tau2-bench/opd/run_tau2_opd_airline_retail.sh)第311–316行。

记 `b` 为生成该 token 的行为策略，`p` 为训练前的当前学生，`q` 为教师。v1/v2 用 `A=log(q)-log(p)`；实际命令同时启用 `--use-tis --tis-clip 2 --tis-clip-low 0`，并且 `use_rollout_logprobs=False`。

在固定上下文、重要性权重未截断、当前更新起点上，loss 梯度是：

`E_b[(p/b) * (log p - log q) * ∇log p] = ∇ KL(p || q)`。

因此，日志中未加 TIS 权重的 `E_b[log p-log q]` 可以为负；这不证明实际经过 TIS 的梯度在强化旧行为。README 写出的 `KL(b||q)-KL(b||p)` 是该未加权日志的条件期望，不能直接作为训练梯度的诊断。实际实现仍有权重截断、旧上下文分布和推理/训练数值差异，不能据此宣称整个异步过程无偏。

v3 将 advantage 改成 `log(q)-log(b)`，但保留同一 TIS 和 PPO ratio。上述条件下，得到的是 `∇[KL(p||q)-KL(p||b)]`，而非当前学生的 reverse-KL 梯度。

数值复现使用源码中的 `compute_advantages_and_returns`、`compute_policy_loss` 和 `vanilla_tis_function`。取 `p=q=[0.8,0.2]`、`b=[0.5,0.5]`，TIS 权重 `[1.6,0.4]` 均未截断：

| 梯度（对学生 logits） | 结果 |
|---|---|
| 精确 `KL(p||q)` | `[0, 0]` |
| v1/v2 current-logprob + TIS | `[0, 0]` |
| v3 behavior-logprob + TIS | `[-0.221807, +0.221807]` |

v3 会把已经等于教师的学生继续推离教师。另两个对照也通过：`b=p` 时两条实现都匹配精确梯度；`b≠p≠q` 且不触发截断时，仅 current-logprob 版本匹配精确梯度。

源码引用的 [Tinker OPD 实现](https://github.com/thinking-machines-lab/tinker-cookbook/blob/main/tinker_cookbook/distillation/train_on_policy.py)确实使用 sampled logprobs，但其训练循环是同步采样、训练、更新 sampling client。这不能作为无限 policy lag 下同一公式无偏的依据。这里的判断依据是上面的源码复现与推导。

建议：停止把该默认开关和 v3 结果称为“无偏修复”。若目标仍是当前学生在所收集上下文上的 reverse-KL，保留 current-logprob + TIS，并单独处理采样陈旧程度。现有 OPD preflight 测试覆盖路由和对齐，没有检查这个梯度条件。

## 2. 高优先级：完成队列积压，加上单次更新缺少 PPO clipping 约束

[continuous.py](../../../examples/tau2-bench/rl/continuous.py)第186–207行在 unlimited-lag 分支只约束 `len(groups)-len(ready)` 和 `inflight`，并不限制完成队列。`ready` 主要受剩余总训练预算限制；第315–317行再按完成顺序消费它。`pool_capacity=32` 不表示最多缓存32条待训练轨迹。

| 观测 | v1：2e-6，20 updates | v2：1e-5，60 updates |
|---|---:|---:|
| ready 队列最大长度 | 96 | 219 |
| 首个 Assistant turn 到消费的平均 lag | 3.67 | 8.62 |
| 最大 lag | 9 | 17 |
| v2 每20步的平均 lag | — | 4.02 / 8.56 / 13.28 |
| TIS 截断比例，按现有 loss 权重取均值 | 0.0016% | 0.2189% |

v2 Airline / Retail 最后一个 Assistant turn 到消费仍平均落后7.69 / 7.27步；滞后不仅来自长对话跨版本，还明显来自排队。README 的 v2 平均 lag7.2、后段约11，与完整60步日志复算值不符。

TIS 修正的是给定历史下的 token 概率，不能把旧历史变成当前策略新生成的历史。截断比例低也不等于上下文分布新鲜。应为 `ready + 正在生成` 设置明确的总预取预算并施加回压，记录按域和按 token 的实际 lag；不应只改 advantage 分子来处理积压。

当前4环境进程路径在第126–128行明确拒绝有限 lag，且 OPD launcher 硬编码4进程和 `lag=-1`。因此不能仅设置一个外部 `TAU2_MAX_POLICY_LAG=1` 就得到有效对照；需要先使配置可覆盖，并用已有单进程有限 lag 路径做对照，或给多进程 producer 增加完成队列回压。队列上限本身也不保证长轨迹的最大版本跨度。

此外，两次运行的 `train/pg_clipfrac=0`、`train/ppo_kl=0` 在全部80个更新上成立。当前每批只做一次 optimizer step，PPO denominator 是训练前重新计算的当前学生 logprob，所以反向时 ratio 为1。这是该配置的正常数学结果，**不能把 eps_clip0.2 当成更新后策略偏移的约束**。TIS clipping 与 PPO clipping 是两个不同环节；LR 放大5倍的风险仍需用实际更新后的 KL/评测判断。

## 3. 实验复算：Retail 超教师尚未确立，Airline 不是样本占比不足

复算了7个模型/检查点的21份域结果，共2,800条 official simulations。Airline / Retail / Telecom 的任务对象、task ID、逐 trial seed、Agent/User 配置和环境信息与 SFT4505 一致；三个 pass 指标均与 summary 一致。OPD 三域的并发分配是2/2/5，SFT/专家四域是1/2/2/4，并且均有 slot borrowing，所以服务调度并非完全相同。顶层 BM25 字段差异仅作用于 Banking，不改变这三个域的检索配置。未发现评分分母错误或错用模型的证据。

## 4. 已核对的正确路径与剩余限制

- 教师配置正确映射 Airline iter29 / Retail iter9；两者的模型 config、tokenizer.json、tokenizer_config.json、vocab.json、merges.txt 与 SFT4505 逐文件直接比较一致。
- 学生确实从 SFT4505 加载，v1/v2 训练命令的行为开关未启用；v3 才启用。纯 OPD 的任务 reward 为0，`normalize_advantages=False`，关闭 GRPO std normalization 和零信号组替换。K=1 的 zero-variance-group rate恒为100%是预期，不是训练失败。
- 教师收到的是学生的原始 token context；disjoint segments 分别打分后按 response suffix 对齐。回放全部1,280条已消费轨迹，Assistant 输出 token 总数、segment mask 总数和记录的训练响应 token 数完全一致。User/tool 注入文本不进入 loss；按整个 rollout 的 mask 总数归一化，未发现多 segment 重复放大权重的路径。
- 这是 token 层纯 OPD：原来的 progress-db-count/turn credit 没有继承，也没有 task success 优选教师轨迹。这是显式配方选择，不是 credit assignment 已经参与蒸馏。若要动作加权或 task reward 混合，应作为后续独立实验。
- 一个次要可观测性问题：`loss.py:1114` 的 `train/opd_reverse_kl` 依赖 batch 中存在该字段，但 `model.py:578–596` 的训练 `get_batch` keys 未包含它，因此这条训练指标未输出。`rollout/opd_reverse_kl` 仍有记录，梯度本身不受此缺字段影响；也没有分域 teacher-KL/TIS 指标。
- 本次没有重新运行完整 Megatron/SGLang 集群测试，也没有在线重算教师 logprob；dump 发生在教师请求之前，不含教师响应。已有 job 日志记录14项 OPD测试、114项通用预检通过。本次新增证据是实际 loss 函数的CPU梯度复现、1,280条消费轨迹回放和2,800条评测结果复算，不能把历史 preflight 通过视为异步目标正确的证明。

## 5. 下一步的最小顺序

1. 修正 v3 的目标解释与默认设置；保留“学生等于教师但 behavior 陈旧时梯度为零”的回归检查。给完成队列加回压，并验证配置实际生效。
2. 用相同 SFT4505、两位教师、User、数据比例、batch16、K1、LR和更新预算，对比有/无完成队列回压。先隔离陈旧采样影响，再单独变动 LR；不同时提高 LR、延长预算和改 advantage 公式。现有 v1/v2 不能单独识别这些因素。
3. 记录分域 teacher KL、TIS/lag、raw success、动作/DB指标；把未加权 log-ratio 与经过重要性权重的目标统计分开。若需要 KL 曲线，用新鲜学生轨迹或明确标注权重/采样分布。
4. 用固定并发配置补 seed301 的同口径 SFT、教师与候选 OPD 评测，再决定是否扩到四域、调整域比例或引入动作级 credit。不要根据一次 Retail 点估计或 KL 符号直接选择配方。
