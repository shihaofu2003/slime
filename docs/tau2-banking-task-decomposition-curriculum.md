# Tau2 Banking 任务分解与课程构造方案

## 背景与核心判断

当前目标不是继续仿写 Tau2 Banking 的完整任务，而是先理解其能力和业务结构，再在独立生成的新场景中构造可学习、可验证、难度递进的训练任务。

**评测隔离修正（2026-09-06）：**97 条 Tau2 Banking benchmark 任务将全部用于最终评测。因此，任何从某条 benchmark 任务直接派生的完整任务、事实题、检索题、决策题或单动作题都属于评测派生数据，只能用于能力诊断和验证构造工具，不能进入 SFT、GRPO 或 OPD。训练任务必须是在相同 Banking 环境接口和业务规则下独立生成的新场景，不能复用 benchmark 的用户请求、实体、初始状态、required-document 组合、动作参数或动作链。

直接复制原任务形态存在两个现实问题：

- Qwen3-4B-Instruct-2507 对大部分 Banking 任务完全失败。对 GRPO 而言，同组 rollout 全部为 0 时缺少有效的组内优势信号。
- Qwen3.5-4B non-thinking 也很少端到端成功，难以通过简单的成功轨迹筛选获得足够多的优质示范。

因此，一条原始复杂任务不应直接被视为一个不可拆分的训练样本。更合适的表示是：

```text
业务目标
  → 所需证据
    → 推理与决策
      → 用户交互
        → 工具动作
          → 环境状态
            → 完成或转人工
```

这张依赖图上的每个节点可以先构造成诊断探针，用于确认能力缺口。真正的训练任务应在新场景上复现相同能力结构；只有模型掌握前置节点后，才逐步组合成独立的完整工作流，不能恢复或改写成某条 benchmark 任务。

benchmark 困难任务没有成功轨迹时，仍可用于能力诊断，但无论是否得到成功轨迹都不能转为训练数据。对于后续独立生成的新任务，如果暂时没有可验证的成功教师轨迹，则可作为课程终点或内部挑战集；在得到正确轨迹或有效局部 credit 前，不作为 SFT/OPD 正例，也不直接作为全二元奖励的早期 GRPO 数据。

## 原始 Benchmark 盘点

运行时任务以 `../tau2-bench/data/tau2/domains/banking_knowledge/tasks/task_*.json` 为准，知识库位于同领域目录的 `documents/`。聚合文件 `tasks.json` 有 13 条任务与运行时文件不同，因此只作为漂移对照，不作为构造输入。

当前测试集包含 97 个任务，知识库包含 698 篇文档。文档平均约 189 个英文词，中位数约 151 个词。

每条任务声明的 `required_documents` 数量如下：

| Gold 文档数 | 任务数 |
|---:|---:|
| 1 | 7 |
| 2–4 | 12 |
| 5–8 | 26 |
| 9–12 | 26 |
| 13–16 | 14 |
| 17 以上 | 12 |

平均每个任务需要 9.89 篇文档，中位数为 10，最多为 30。52/97 的任务涉及至少 9 篇文档，26/97 涉及至少 13 篇文档。

每条任务的 `evaluation_criteria.actions` 数量如下：

| 期望动作数 | 任务数 |
|---:|---:|
| 1 | 11 |
| 2–4 | 19 |
| 5–8 | 20 |
| 9–16 | 31 |
| 17 以上 | 16 |

期望动作数平均为 9.56，中位数为 8，最长动作链为 33。这里的动作既包括真实业务操作，也包括身份验证、发现工具、解锁工具、调用工具、把工具交给用户以及用户执行工具。

任务结构还有以下特点：

- 81/97 个任务要求身份验证。
- 69/97 个任务要求发现并调用动态 Agent 工具。
- 21 个任务要求 Agent 向用户提供动态工具，其中 20 个任务要求用户随后调用该工具。
- 87 个任务仅以最终数据库状态判定，1 个任务同时使用数据库状态与自然语言断言，另有 9 个任务以动作匹配为依据。
- 97 个任务的 `communicate_info` 均为空，成功主要由动作和最终状态决定。

这表明 Banking 不是单纯的知识问答，而是检索、多文档推理、信息收集、身份验证、工具发现、状态修改和用户模拟器协作的组合任务。

按 Gold 文档数统计，现有模型的单轨迹成功情况如下：

| Gold 文档数 | Qwen3 两次评测 | Qwen3.5 non-thinking |
|---:|---:|---:|
| 1 | 10/56 | 4/28 |
| 2–4 | 8/96 | 4/48 |
| 5–8 | 6/208 | 6/104 |
| 9–12 | 3/208 | 1/104 |
| 13 以上 | 0/208 | 0/104 |

按动作长度统计，17 步以上的任务两个模型均为 0 成功。文档数和动作数与业务类型、实体数等因素相关，因此不能单独解释因果，但足以说明原始复杂任务不适合作为早期成功轨迹的主要来源。

Qwen3 每条 Banking 轨迹平均搜索约 1.27 次，Gold 文档微平均覆盖率约 17%；Qwen3.5 平均搜索约 4.98 次，覆盖率约 41%。Qwen3.5 找到的正确文档明显更多，但最终只成功 15/388，Qwen3 两次分别成功 13/388 和 14/388。这说明提高检索覆盖是必要条件，但不足以解决完整任务。

Qwen3.5 轨迹包含 491 个匹配的正确写动作，Qwen3 两次分别只有 93 和 105 个；然而 Qwen3.5 的最终 DB 完全匹配仍只有 21 条。很多失败轨迹实际包含正确的局部检索、判断或动作，只是遗漏任意一个必要子任务后，最终二元奖励仍为 0。

| 身份验证与资料变更 | 2 | 身份验证、邮箱修改、拒绝或转人工 |

| 交易争议、购买保护与补卡 | 9 | 欺诈、重复扣款、未收到商品、临时退款 |

当前两个模型在返现核算、交易争议、信用卡销户、信用额度调整、组合开户、多卡遗失、PIN 锁定和储蓄利息等复杂类别中几乎没有端到端成功。因此，后续构造应复用这些业务内容，但不能照搬其原有组合复杂度。

## 单条任务的分解结构

每条原始任务应拆成六类信息。业务内容和原子能力必须分别记录；例如“信用卡申请”是业务内容，“比较产品并按约束筛选”是原子能力。

| 部分 | 建议记录内容 | 作用 |
|---|---|---|
| 业务内容 | 产品族、具体业务、查询/推荐/执行/拒绝、目标实体数 | 控制任务讲什么业务 |
| 知识证据 | Gold 文档、决定性文档、候选文档、事实数、实际命中与干扰文档 | 控制检索和证据复杂度 |
| 推理操作 | 抽取、过滤、比较、计算、分类、例外判断 | 明确模型需要怎样处理证据 |
| 对话交互 | 隐藏用户信息、追问、身份验证、用户施压、用户工具协调 | 控制对话难度 |
| 工具与状态 | 读/写动作、动态工具、实体数、依赖顺序、不可逆操作 | 控制 Agent 工作流 |
| 成功条件 | 正确证据、实体、动作、参数、中间状态和最终状态 | 支持验证与局部 credit |

文档数量至少应区分以下口径：

| 文档指标 | 含义 |
|---|---|
| Gold 文档数 | benchmark 声明为相关的全部文档数量 |
| 决定性文档数 | 缺少其中任意一篇就无法确定答案的文档数量 |
| 候选比较文档数 | 产品筛选或规则比较时必须考虑的文档数量 |
| 事实数量 | 最终决策需要提取的独立事实数量 |
| 实际检索文档数 | 轨迹真正返回的文档数量 |
| Gold 命中文档数 | 实际检索命中的 Gold 文档数量 |
| 干扰文档数 | 检索返回但与当前决策无关的文档数量 |

文档数不能作为唯一难度指标。例如：

- `task_001` 依赖 4 篇文档和 1 个动作，主要难点是产品比较和约束过滤。
- `task_034` 依赖 2 篇文档和 9 个动作，主要难点是多轮转人工交互。
- `task_071` 依赖 30 篇文档和 6 个动作，主要难点是跨商业支票与商业储蓄两类产品推荐。
- `task_080` 依赖 19 篇文档和 30 个动作，文档、实体和操作链均复杂。

建议将任务表示成简单的依赖图，而不是把所有因素压缩成一个机械分数：

```text
用户目标与已知信息
  → 待补充信息
  → 检索查询
  → 决定性文档与事实
  → 业务判断
  → 工具与参数
  → 状态检查
  → 下一子任务或终止
```

## Banking 原子能力表

一条任务可以包含多个原子能力。应标记主要能力和辅助能力，并说明依赖关系，而不是强制每条任务只有一个标签。

| 原子能力 | 具体含义 |
|---|---|
| 查询构造 | 将用户问题改写为能命中知识库的搜索词 |
| 检索覆盖 | 找到完成当前决策所需的全部决定性文档 |
| 文档相关性判断 | 区分个人、商业、通用规则和干扰文档 |
| 单文档事实抽取 | 提取年费、APY、额度、资格等事实 |
| 跨文档比较 | 在多个产品或规则之间进行比较 |
| 约束过滤 | 先满足硬条件，再按用户偏好排序 |
| 数值计算 | 计算返现、利息、费用和额度 |
| 用户信息补全 | 只追问当前决策真正缺失的信息 |
| 身份验证 | 在读取或修改账户前完成规定验证 |
| 实体—状态绑定 | 将交易、卡片、账户和状态绑定到正确用户 |
| 工具发现 | 找到并解锁当前业务所需的动态工具 |
| 动作选择 | 选择查询、争议、冻结、关闭、补卡等动作 |
| 参数构造 | 使用真实账户 ID、交易 ID 和业务原因 |
| 前置条件检查 | 写操作前检查资格、时间窗口和账户状态 |
| 动作顺序 | 按依赖关系完成读取、判断、写入和验证 |
| 用户工具协调 | 正确提供用户工具，并引导用户在合适时机调用 |
| 观察后恢复 | 工具失败或状态不符时更新判断并重新规划 |
| 子任务覆盖 | 多卡、多账户或多交易任务中不遗漏对象 |
| 拒答与转人工 | 知识不存在或权限不足时停止猜测 |

例如信用卡推荐任务可以表示为：

```text
查询构造
  → 检索各候选卡文档
    → 抽取费用、收益和资格
      → 按硬约束过滤
        → 询问缺失用户信息
          → 推荐唯一产品
            → 调用申请工具
```

## 难度递进与任务构造

难度应该通过逐步组合原子能力形成，并尽量一次只增加一个主要复杂因素。

| 阶段 | 任务结构 | 主要训练目标 |
|---|---|---|
| L1 知识原子 | 提供 1 篇相关文档，询问 1 个事实，无工具 | 事实抽取 |
| L2 单文档检索 | 1 篇 Gold 文档隐藏在小型语料中，回答 1 个问题 | 查询构造与相关性判断 |
| L3 单决策 | 1–2 篇文档、1 个实体、1 个业务条件、至多 1 个写动作 | 资格判断或动作选择 |
| L4 受控组合 | 2–4 篇文档，只组合 2 个原子能力，2–4 个动作 | 比较、过滤与单次执行 |
| L5 中等工作流 | 4–8 篇文档、1–2 个实体、一次追问或恢复 | 读、判断、写和验证 |
| L6 Benchmark 式组合 | 多产品族、多实体、多写操作、动态工具和用户协作 | 端到端综合能力 |

L1–L6 是课程阶段，不是由固定权重计算出的难度分数。实际分析仍应保留文档、事实、实体、动作、分支和对话等原始维度。

每个复杂原任务建议派生以下版本：

- `evidence-given`：直接提供决定性证据，只训练下游推理和动作。
- `retrieval-only`：只要求找到相关文档，不执行银行操作。
- `decision-only`：提供证据和状态，只要求作出业务判断。
- `single-action`：提供判断结果，只要求完成一个正确工具动作。
- `two-skill-composition`：组合两个已经掌握的原子能力。
- `full-composition`：当前历史产物中恢复接近原 benchmark 的完整任务，仅作诊断，禁止训练；后续以独立生成的 `synthetic-full-workflow` 取代。

上述六种形态描述了已经完成的 benchmark 派生诊断集。它们不能通过按 `source_task_id` 切分变成合格训练集，因为最终评测覆盖全部 97 条源任务。后续训练数据只能从独立生成的新场景派生 evidence、retrieval、decision、single-action、two-skill 和完整工作流版本。

以 `task_001` 为例，原任务需要比较 4 张信用卡，处理年费、返现和隐藏的 Rho-Bank+ 订阅信息，最后让用户申请。可以依次拆为：

1. 从一篇卡片文档提取年费和返现率。
2. 从知识库检索指定卡片文档。
3. 比较 Gold 与 Silver 两张卡的年费。
4. 根据“不能接受年费”过滤四张卡。
5. 判断是否需要询问 Rho-Bank+ 订阅状态。
6. 在条件完整时推荐唯一产品。
7. 给定推荐结果，正确调用申请工具。
8. 最后仅作为诊断探针组合成原任务；训练中的完整任务必须换成独立的新场景。

以 `task_071` 为例，应先分别构造商业支票和商业储蓄的事实抽取、两产品比较和单类别推荐，再组合两个产品族，不能一开始就要求模型同时处理 30 篇文档。

以 `task_080` 为例，应从单张借记卡冻结、单张借记卡关闭补卡、单张信用卡关闭补卡开始，再扩展到两张卡和五张卡。卡片数量应作为单独的难度轴控制。

## 教师轨迹的获得方式

以下逐节点教师流程只适用于独立生成并通过环境验证的新任务。benchmark 的 `required_documents`、`evaluation_criteria.actions`、期望参数和最终 DB 状态可以用于分析模型失败，但不能用于生成训练轨迹或训练动作骨架。

推荐流程如下：

```text
确定当前子目标
  → 提供或检索相关证据
  → 教师生成当前一步
  → 环境执行
  → 检查实体、参数和状态
  → 正确则进入下一节点
  → 错误则只重试当前节点
```

生成教师轨迹时，可以在教师侧提供 Gold 文档、当前子目标、已完成子任务和下一步允许的动作集合。这些信息只用于生成控制，不进入最终学生可见的消息。生成结果仍必须在真实环境中执行验证。

对完整失败轨迹，应保留经过验证的正确局部片段，例如：

- 命中 Gold 文档的查询；
- 正确的文档事实抽取；
- 正确身份验证；
- 正确实体定位；
- 正确单次写操作；
- 正确的错误恢复。

不得因为轨迹中包含若干正确动作，就把整条最终失败轨迹标为正例；也不应因为最终奖励为 0，就丢弃所有正确局部片段。

## 训练任务池与奖励使用

只有独立生成的新场景才能按下表进入训练任务池。所有带 benchmark `source_task_id` 的现有派生任务统一放入 `benchmark_derived_diagnostic`，无论模型是否成功，都不具备训练资格。

| 任务池 | 用途 | 要求 |
|---|---|---|
| 能力习得池 | SFT/OPD | 原子和中等任务，有环境验证通过的正确轨迹 |
| 学习前沿池 | GRPO | 当前模型有成功也有失败，能够产生组内优势差异 |
| 挑战评测池 | 最终评测 | 原始复杂任务或当前全失败任务，不要求立即产生教师轨迹 |

对于 GRPO，不应长期采样全 0 或全 1 的任务组。全 0 任务没有成功行为可强化，全 1 任务也缺少区分度。课程应持续把主要 rollout 预算放在模型当前的学习前沿，同时保留少量已掌握任务作为行为锚点和少量困难任务观察迁移。

训练 credit 应对应任务依赖图中的真实子目标，例如：

- 是否找到决定性文档；
- 是否提取正确事实；
- 是否绑定正确实体；
- 是否满足业务前置条件；
- 动作和参数是否正确；
- 写操作后的状态是否正确；
- 是否覆盖全部子任务。

不能继续以“调用了更多工具”或“工具名正确”为主要训练信号。官方二元任务成功仍作为 held-out 评测标准，局部 credit 只用于改善训练信号和定位因果回合。

## 建议执行顺序

第一阶段保留已经完成的 97 条 benchmark 清单和能力统计作为诊断资料，不再从逐任务 gold 标注生成训练数据。benchmark 任务、派生任务和已有轨迹全部隔离于 SFT、GRPO 和 OPD 输入。原任务清单仍记录：

- 业务类别和具体业务；
- Gold、决定性和候选比较文档数；
- 实体数和子任务数；
- 推理操作和原子能力集合；
- 读取、写入和用户动作数；
- 动态工具、身份验证和信息追问；
- 中间检查点与最终状态；
- Qwen3/Qwen3.5 的检索覆盖、局部动作和最终成功情况。

第二阶段只从 Banking 知识库、工具 schema、数据库 schema 和业务约束提取可复用的任务模板，不把 benchmark 的具体用户请求、实体值、required-document 集合、动作参数或动作顺序带入模板实例。

第三阶段从四类代表业务开始独立生成新场景：

1. 信用卡选择与申请资格；
2. 单笔返现或交易争议；
3. 单一支票或储蓄账户推荐；
4. 单卡遗失、PIN 锁定或补卡。

第四阶段为每个新场景生成 evidence-given、retrieval-only、decision-only、single-action、两能力组合和 `synthetic-full-workflow`，使用新的实体、初始状态、用户表达和合法动作组合，并通过真实环境参考执行验证。随后显式检查其用户请求、实体、状态和动作链没有复现任何 benchmark 实例。

当前已经完成从 pilot 到全量诊断池的第一轮放大：保留 `task_001`、`task_031`、`task_071`、`task_036` 的 24 条手工诊断任务，并将其余 90 条可回放源任务按同样六种形态展开。最终覆盖 94 个源任务、15 类业务，共 564 条任务规格，即每种形态 94 条；难度分布为 L1 94、L2 94、L3 188、L4 104、L5 31、L6 53。`task_051`、`task_077`、`task_083` 因当前参考链与环境不兼容，仅保留在 97 条源任务清单中，没有进入扩展池。

模型烟测发现，若把原子任务指令只放在 User 模拟器的隐藏场景中，User 可能自己说出 gold label，而 Agent 即使语义正确也会因严格字符串检查得 0。现已将 470 条分解任务改为固定首条用户请求：Agent 直接看到任务及输出格式占位符，gold 值不出现在请求中。进一步的真实对话烟测还发现，直接继承源任务的全部 User 工具会让已正确完成的原子操作因无关后续操作而产生 DB 假失败；因此非完整任务现在采用有界 User：首次实质回答后终止，仅暴露该子任务实际评分的 User 工具，Evidence/Decision 的目标也改为已解析的最终业务操作。为避免“最相关句子”与严格字符串评分产生歧义，系统化 Evidence 请求还提供章节与行序号或表格首列键作为无答案定位信息。94 条完整组合任务保持原始对话入口和工具集合。

扩展产物位于 `output/experiments/tau2-banking-task-curriculum/`，已完成以下验收：

- 17 个零 GPU 单测通过，其中包含原子任务 User 工具边界、终止协议、节点级扩展和恢复结果覆盖；
- 564 条任务及其成功契约通过静态唯一性、来源映射、文档存在性、动作对齐、奖励边界和完整任务同源检查；
- 94 条 retrieval-only 参考查询全部在真实 BM25 top 10 中命中目标文档，本地同算法复现的最差名次为第 3；
- 真实 Tau2 Banking 环境完成 564 条 schema 校验和 564 条参考回放，扩展任务错误为 0；
- 97 条源参考链仍完整回放用于诊断，其中 7 个调用错误集中在上述 3 条已排除源任务。

随后使用 `/mnt/afs/models/Qwen3.8-27B` 同时作为 Agent 和 User，对 564 条任务各生成一条真实环境轨迹。Agent 使用 xhigh thinking，User 关闭 thinking。初始 8K 输出协议得到 327/564；其中 16 条是生成或上下文协议失败，不能与业务答错混在一起。通过 16K、262K context、必要时 TP2，以及对最难样本使用 32K compact-history 恢复后，16 条都得到有效轨迹，最终精确成功为 329/564（58.33%），终止分布为 563 条 `user_stop` 和 1 条 `max_steps`，不再有 infrastructure error。保守的首次尝试成功率是 315/564（55.85%）。

恢复后的六种任务结果为：retrieval-only 93/94（98.94%）、decision-only 84/94（89.36%）、evidence-given 58/94（61.70%）、single-action 48/94（51.06%）、full-composition 32/94（34.04%）、two-skill composition 14/94（14.89%）。这说明 Qwen3.8 的 Banking 检索和单节点能力较强，但能力组合仍然是主要缺口；长完整任务还显著增加推理耗尽和上下文压力。

在第一轮结果基础上，已按依赖图节点继续扩展 2,740 条任务：933 条逐事实 evidence-given、933 条对应 BM25 retrieval-only，以及 874 条带正确前置状态的逐动作 single-action。它们覆盖同一批 94 个可回放源任务和全部 15 类业务。17 个单测、静态校验、2,740 条真实环境 schema 校验与参考回放均通过，933 条 BM25 参考查询全部命中目标文档。

双 Qwen3.8 对这 2,740 条任务的精确成功为 2163/2740（78.94%），全部以 `user_stop` 结束且 infrastructure error 为 0。其中 retrieval-only 为 932/933（99.89%），evidence-given 为 578/933（61.95%），single-action 为 653/874（74.71%）。Agent 请求的动作检查通过率为 90.50%，User 请求的动作检查通过率为 42.16%，因此后续仍需单独关注 User 工具协作，即使 Agent 和 User 使用同一权重。

当前两批合计 3,304 条可执行的 benchmark 派生诊断规格、2,492 条 Qwen3.8 环境成功轨迹（75.42%）。此前的行为锚点、GRPO 学习前沿和 SFT/OPD 候选划分现已撤销；全部 3,304 条任务及其轨迹统一隔离，不得用于训练。它们的有效用途是测量不同原子能力、验证任务接口以及指导新场景的难度配比。

下一轮扩容从新的 Banking 场景开始，优先生成 evidence 与 single-action 的用户表达、实体和状态变化，再用真实环境参考回放和 Qwen3.8 轨迹筛选验收。retrieval-only 已接近饱和，不按同等比例扩增；two-skill 应先改善组合训练信号；完整任务只能由新场景的已验证节点组合而成。最终原则是先生成独立、可验证的能力节点，再逐步组合成新的完整任务，使训练信号落在正确证据、动作、参数和最终状态上，同时保持 benchmark 完整隔离。
