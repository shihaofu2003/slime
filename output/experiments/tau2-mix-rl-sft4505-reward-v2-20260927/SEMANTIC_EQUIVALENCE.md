# 从具体反例到跨领域性质

目的：将数值格式、参考状态同步和批量更新错误归到可验证的共性问题，补充前一轮按领域排查的遗漏。2026-09-27，本轮只执行 CPU 回放诊断，没有提交训练或修改原环境实现。

## 表示变化应保持业务含义

`2` 与 `2.0` 是“数值相同、表示不同”的反例。更广泛的要求是：在工具/字段约定允许的等价变换下，业务结果、终局奖励和状态势函数应保持一致。只修复最终 DB 比较不足以保证这一点；表示可能先进入文本、业务 ID 或嵌套 JSON，再影响状态和评分。

| 环节 | 已发现的反例 | 应验证的性质 |
|---|---|---|
| 参数到业务状态 | Banking 收入或交易金额的数值格式改变业务 ID；Telecom 充值量改变账单文本 | 等价参数产生等价业务状态，生成文本/ID 前使用字段约定的数值表示 |
| 状态到奖励 | Airline 相等数值因序列化不同被判 DB 失败 | 相同字段值获得相同 reward 与 progress；两者使用相同的状态比较语义 |
| 参数到 ACTION 评分 | Banking 的 JSON 字符串被按原文比较 | 文档明确为 JSON 的参数按解析后的结构比较，接受键顺序、空格及等值数值的差异 |

当前公共工具分发 `ToolKitBase.use_tool` 直接调用 `self.tools[tool_name](**kwargs)`；函数的类型标注没有在这里执行数值规范化。Banking 的嵌套工具入口也直接调用解析参数。因此类型/格式差异可以沿整条链路传播，终点的结构化比较无法还原已经改变的 ID。

等价关系必须服从字段含义：数值字段的 `2`/`2.0` 可相等；字符串 ID `"002"` 与 `"2"` 保持不同；布尔值不当作金额；金额精度按业务规则确定。普通字符串不自动尝试 JSON 解析，所有列表也不能统一排序，重复商品数量和有业务含义的执行顺序必须保留。

## 按此性质复查后新增的证据

前一轮数值检查遍历了 JSON 对象/数组，但没有进入被编码为字符串的 JSON 参数。本轮对 Banking 文档明确使用此格式的三个工具入口进行等价变换，使用 v2 工具/评分实现，固定任务和初始状态，执行原黄金动作及变换后的动作，再计算 DB、ACTION 和最终奖励。共 298 组配对回放，原表示的奖励全部为 1，工具响应的 error 标记全部为空。

| 等价变换 | 配对任务数 | 最终 DB 快照相同 | ACTION 通过变失败 | 最终 reward 1→0 |
|---|---:|---:|---:|---:|
| 只改变 JSON 排版/键顺序 | 209 | 209 | 209 | 17 |
| 只改变 JSON 内数值的整数/浮点表示 | 89 | 73 | 89 | 21 |

两组任务有交集：最终 reward 发生误判的任务合计 33 个。排版变换影响的 17 个任务按 ACTION 评分；数值变换影响的 21 个任务中，16 个按 DB 评分，5 个按 ACTION 评分。这些是构造等价动作后的可复现任务数，不是现有 rollout 失败率，也不是模型提分。

新增的 16 个 DB 差异来自 `apply_checking_account_credit_5829` 和 `deposit_check_3847` 的交易 ID。例：`banking_syn_v1_train_000588_l3_single_action` 将 `amount=6.0` 改成 `amount=6`，账户变动金额相同，生成的交易 ID 不同，reward 从 1 变成 0。此前只统一信用卡申请收入的局部修复没有覆盖这两个入口。

证据：[统计](representation_equivalence_summary.json)、[逐任务结果](representation_equivalence.jsonl)、[交易 ID 反例](representation_equivalence_example.json)。复现：[check_representation_equivalence.py](check_representation_equivalence.py)。结果中的 `same_db_state` 表示 v2 结构化 DB 快照相等，包含 ID 字段。

## 其他问题也应按性质分组

| 问题类别 | 已知例子 | 跨领域检查方式 |
|---|---|---|
| 执行路径一致性 | Telecom 黄金回放缺少同步 | 同一初始状态和动作序列在 live、回放、参考构造中产生相同状态 |
| 状态更新正确性 | Retail 多商品更新复用了最后一个 variant | 商品与新规格逐项对应；独立修改成对换序后结果一致；重复商品计数不变 |
| 奖励与 credit 一致性 | 原终局全错组仍可能有 progress 信号；错误目标影响密集奖励 | 检查终局成功条件、势函数目标、credit 对齐及组过滤是否使用一致的任务含义 |
| 统计与优化波动 | 小任务组数、随机难度混合、条件筛选、异步版本差异 | 固定任务分布和评估协议，区分估计噪声、选择偏差和策略实际变化 |

## 修复应落在共同边界

实现方向是：按已声明的参数类型在实际工具执行前统一等值数值，包括解析后的嵌套参数；业务 ID 和生成文本使用这些统一后的输入；ACTION 对明确编码为 JSON 的字段比较解析结构；终局 DB 与 progress 继续共享状态语义。每条规则用等价输入配对回放验证，并保留真实金额、ID、商品数量等变化应改变结果的对照。

这是本轮确定的修复方向，新增的嵌套参数和 ACTION 问题尚未接入 v2 生产入口。现有 v2 不能视为已完整解决“表示等价性”这一类问题。参考同步、商品更新和统计/优化问题仍需各自对应的性质，不能靠一个宽松比较函数统一消除。

这类修复改善奖励的可信度和训练信号；它本身不保证曲线单调上升。此前 Telecom 同轨迹重评分的 +21.30 pp 仍只表示评分纠错量，新增 Banking 任务数也不能直接相加成预期训练收益。
